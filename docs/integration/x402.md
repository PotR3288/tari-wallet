# x402 over Tari Ootle (dApp integration)

How a dApp sells a protected HTTP resource for XTR using this wallet: the resource server
answers `402` with a quote envelope, the dApp drives the wallet's `x402Pay` /
`x402SignClaim` transaction-request kinds (see
[transaction-requests.md](./transaction-requests.md) for the create/approve/submit flow),
and the settlement facilitator — the Ootle indexer — validates, holds, and broadcasts the
claim. The settlement endpoint's contract is specified in
[`docs/x402-facilitator.md`](../x402-facilitator.md); the client package
(`packages/x402-ootle`, published as `@potr3288/x402-ootle`) implements the whole flow
so dApps don't hand-write it.

## The 402 quote envelope

On a `402` response the server sends a `PAYMENT-REQUIRED` header whose value is the
JSON-encoded quote:

```json
{
  "resourceUrl": "https://api.example.com/protected",
  "resourceSha256": "<optional 64-hex SHA-256 pin for the served body>",
  "amount": "1000",
  "resourceAddress": "resource_0101…0101",
  "claimantAddress": "otl_esm_…",
  "hashLockHex": "<64 lowercase hex SHA-256 of the claim secret>",
  "refundEpoch": 12758,
  "facilitatorUrl": "https://ootle-indexer-a.tari.com/x402/settle",
  "facilitatorPubKeyHex": "<optional indexer identity-key pin>",
  "expiresAt": 1793449319761,
  "maxFee": "50000"
}
```

Every field is validated twice: shallowly by the client package (`validateQuote` — shape,
hex, expiry) and fully by the wallet at `x402Pay` time (distinct, actionable rejection per
failure). The refund deadline is expressed in **chain epochs**, not wall-clock time: the
HTLC's refund leaf is `AfterEpoch(refundEpoch)`, which is satisfied strictly *after* that
epoch — a funder can recover from epoch `refundEpoch + 1` onward.

## Flow

1. `fetch` (wrapped by `pay402`) gets the 402 and parses the quote.
2. `pay()` creates an `x402Pay` transaction request; the user approves; the wallet funds
   the HTLC (an `htlcFund` underneath) and returns the output's commitment, conditions and
   `outputMask` — the client package persists the mask; **dropping it destroys the refund
   path**.
3. The merchant's wallet signs the claim via `x402SignClaim` — sign-only, never
   broadcast — and the sealed payload goes to `POST /x402/settle`.
4. The facilitator holds, the resource is served, the facilitator broadcasts; the claim
   lands on-chain. If the facilitator never broadcasts, the funder refunds after
   `refundEpoch` — enforced by the chain, not by anyone's cooperation (live-verified;
   see the facilitator spec's trust and honesty-semantics section).

## Alignment with the x402 foundation spec (v2)

Cross-checked against `specs/x402-specification-v2.md` and
`specs/transports-v2/http.md` in the x402 foundation repo (`coinbase/x402`). The
concepts map cleanly; the wire shape deliberately deviates in four places:

| Foundation v2 `PaymentRequired` | Ootle envelope | Note |
|---|---|---|
| `accepts[]` array of scheme objects | flat top-level envelope | v1 has one payment method per resource; the flat shape is what the wallet validates and the popup renders. |
| `accepts[0].extra` (scheme-specific keys) | the Ootle fields themselves (`hashLockHex`, `refundEpoch`, `facilitatorUrl`, …) | these are exactly the "scheme-specific extra" the v2 spec reserves `extra` for. |
| `scheme: "exact"`, `network` CAIP-2 (`eip155:84532`) | absent; no scheme/network fields | a Tari Ootle mechanism would register as scheme `exact`, CAIP-2 `tari:<network>` (namespace not yet in the CAIP registry — an upstream PR must propose it). |
| `asset` (contract address / ISO 4217) | `resourceAddress` | XTR is a native resource address, not a token contract. |
| `payTo` | `claimantAddress` | the HTLC claimant is the payee. |
| `maxTimeoutSeconds` (wall clock) | `refundEpoch` (chain epochs) + `expiresAt` | epochs are the chain's own clock; wall-clock `expiresAt` bounds the quote itself. |
| `x402Version: 2`, `error`, `resource{}`, `extensions` | absent | no client-side version negotiation in v1 of the Ootle rail; the envelope is self-describing. |

**Transport deviation — deliberate.** The v2 spec's canonical HTTP transport carries the
`PaymentRequired` object **base64-encoded** in the `PAYMENT-REQUIRED` header, and client
payment authorization as a base64 `PAYMENT-SIGNATURE` header. The Ootle rail sends the
quote as plain JSON in the same header and has no `PAYMENT-SIGNATURE` analogue at all:
the client's "signature" step is structurally different — the *merchant's* wallet signs
an unbroadcast claim (`x402SignClaim`, status `signed-unbroadcast`) whose sealed payload
is delivered out of band to the facilitator. A client-signed bearer header would be the
wrong shape for hold-then-broadcast settlement, and plain JSON keeps the quote
debuggable in any HTTP client.

**What a foundation-repo contribution needs.** Per the foundation's contributing rules,
a new mechanism starts with a scheme spec under `specs/schemes/` (approved into upstream
`main` before any implementation), one SDK implementation, and an
`e2e/config/mechanisms_<id>.json` catalog entry with the env/testnet/routes blocks. The
catalog entry drafted for Ootle lives alongside this repo's task notes until that spec
PR exists; the shape above is what the spec must pin.
